# Roadmap

Each stage is started with the prompt: `Read CLAUDE.md and docs/roadmap.md, then execute stage N.`
Each stage ends with a pull request (except stage 0) whose description lists every acceptance criterion with its result. Every stage that designs UI uses the skill in `claude/skills/leonardo`.

---

## Stage 0 – Repository setup

**Goal:** A private repository `upinblue/leonardo` with the starter content and a building solution skeleton. No functionality yet.

**Tasks**

1. Add `.gitignore` (`dotnet new gitignore`) and an `.editorconfig` with the standard .NET conventions.
2. Add `Directory.Build.props` (net10.0, nullable enabled, warnings as errors, latest C#) and `Directory.Packages.props` (central package management).
3. Create a solution with empty projects for every entry in the structure in `CLAUDE.md` (tokens generator, WinUI library, WPF library, WinUI gallery, tokens tests). The WPF sample is created in stage 5.
4. Create `.github/CODEOWNERS` with the login from `gh api user --jq .login`, after Bastian has confirmed it.
5. `git init -b main`, commit everything as the initial commit.
6. Create the repository in the organization and push: `gh repo create upinblue/leonardo --private --source . --remote origin --push --description "Leonardo – the design language of up in blue for WinUI 3 and WPF"`.

**Acceptance criteria**

- The repository exists in the organization `upinblue` and is private.
- The solution builds without warnings.
- `CODEOWNERS` contains the confirmed login.
- `brand/`, `docs/`, `tokens/`, `claude/`, `.claude/`, `LICENSE`, `TRADEMARKS.md` and `CLAUDE.md` are unchanged.

## Stage 1 – Tokens and generator

**Goal:** `UpInBlue.Leonardo.Tokens` reads `tokens/leonardo.tokens.json` and generates all platform outputs.

**Tasks**

1. Parse the token file: `$value`, `$type`, `$description`, `$extensions.status`; types `color`, `dimension`, `duration`, `cubicBezier`, `number`; the composite objects under `typography`.
2. Resolve references such as `{palette.brand}`. Unknown references and reference cycles are errors.
3. Generate, each file starting with the header `Generated by UpInBlue.Leonardo.Tokens from tokens/leonardo.tokens.json. Do not edit.`:
   - `src/UpInBlue.Leonardo.WinUI/Themes/Generated/Tokens.xaml`: theme dictionaries Light and Dark with `Color` and `SolidColorBrush` resources for all `theme.*` tokens; a HighContrast dictionary that maps the same keys to system colors; spacing as `x:Double` and `Thickness`; radii as `CornerRadius`; font sizes and line heights as `x:Double`; durations as `Duration`; easing curves as `KeySpline` strings.
   - `src/UpInBlue.Leonardo.WinUI/Generated/LeonardoTokens.g.cs`: a static class with the same values for code (colors, `TimeSpan` durations, easing control points, numbers).
   - `src/UpInBlue.Leonardo.Wpf/Themes/Generated/Tokens.Light.xaml` and `Tokens.Dark.xaml` plus `src/UpInBlue.Leonardo.Wpf/Generated/LeonardoTokens.g.cs`.
   - `generated/apple/Leonardo.xcassets`: one color set per `theme.*` color with light and dark appearance, grouped in a folder `Leonardo`, plus `AccentColor` set to brand in light and far in dark.
   - `generated/apple/LeonardoTokens.swift`: a namespace enum `Leonardo` for iOS and macOS with spacing, radii, densities, spring parameters and the mapping of type roles to SwiftUI text styles, with `#if os(macOS)` where the mapping differs.
   - `generated/web/leonardo.css`: custom properties for light (default), dark (`prefers-color-scheme: dark` and `[data-theme="dark"]`), spacing, radii, type roles in `rem`, easing curves and durations, and a `prefers-reduced-motion` block that shortens motion to crossfades.
   - `generated/presentation/presentation-tokens.md`: a readable table of theme colors, fonts and durations for building the PowerPoint template.
   - Copies of `docs/design-language.md` and `tokens/leonardo.tokens.json` into `claude/skills/leonardo/references/`.
4. Command: `dotnet run --project src/UpInBlue.Leonardo.Tokens -- generate` regenerates everything.

**Tests**

- Reference resolution, unknown reference, cycle detection.
- Contrast in Light and Dark: `textPrimary`, `textSecondary`, `textTertiary` and `link` at least 4.5:1 on `surface`, `surfaceAlt` and `selection`; `onAccent` at least 4.5:1 on `accent`; `strokeStrong` and the three `status*` colors at least 3:1 on `surface`.
- The skill copies in `claude/skills/leonardo/references/` are identical to their sources after generation.
- Determinism: the same input produces byte-identical output.

**Acceptance criteria**

- All tests pass.
- Changing one token and regenerating changes every output that uses it, and nothing else.

**Out of scope:** styles, controls, gallery pages.

## Stage 2 – WinUI foundation and gallery

**Goal:** Apps can reference Leonardo's resources, and the gallery shows the foundations and the first app scenarios.

Design every gallery page with the skill in `claude/skills/leonardo` in build mode, including its research step, and list the Windows design sources you read in the pull request.

**Library tasks**

1. `Themes/Leonardo.xaml` as the single entry point that apps merge after `XamlControlsResources`. It includes the generated tokens.
2. Text styles for the five type roles and for emphasis: `LeonardoPlaceNameTextStyle`, `LeonardoViewTextStyle`, `LeonardoSectionTextStyle`, `LeonardoBodyTextStyle`, `LeonardoBodyStrongTextStyle`, `LeonardoMetaTextStyle`. Add a variant with tabular figures for numbers in columns if WinUI 3 supports it; otherwise document the limitation in the pull request.
3. Accent: map the WinUI accent ramp (`SystemAccentColor` and its Light1–3 and Dark1–3 steps) so that accent fills resolve to `palette.brand` in Light and to `palette.far` in Dark. Derive the remaining steps within the blue scale and list all resulting values in the pull request for confirmation.
4. Content-layer neutrals: provide brushes for the `theme.*` neutrals. Do not override Fluent's own control brushes beyond the accent ramp.

**Gallery tasks**

1. App shell: `NavigationView` on the left, `MicaBackdrop`, MVVM, a theme switch (System, Light, Dark) and a density switch (compact, standard, comfortable).
2. Foundation pages:
   - **Overview:** what Leonardo is and the rule levels.
   - **Color:** blue scale, theme colors in Light and Dark with contrast values.
   - **Typography:** all roles with sample text, including long German compound words to test wrapping.
   - **Grid and geometry:** spacing, radii, the shared alignment line and the concentric radius rule visualized.
   - **Fallbacks:** the live state of transparency, animations, high contrast and text scaling, with instructions how to change each in Windows Settings.
3. Scenario pages, static in this stage and refined in stages 3 and 4. Only WinUI controls plus Leonardo resources:
   - **Files:** folder tree, file list with metadata columns, details pane.
   - **Customers:** list and detail with an editable form and validation.
   - **Approvals:** an inbox of requests to approve or reject.
   - **Overview:** key figures expressed typographically, one small chart.
   - **Activity:** a timeline of events.
   - **Settings:** a typical settings page built from standard controls.
   - **States:** empty, loading, error and offline states.

**Acceptance criteria**

- Every page renders correctly in Light, Dark and high contrast.
- No literal design values outside generated files.
- No Fluent control is restyled apart from the accent ramp.
- Screenshots of every page in Light and Dark are in the pull request.

## Stage 3 – Motion

**Goal:** The seven motions of the design language are available as reusable helpers and visible in the gallery.

**Library tasks** (namespace `UpInBlue.Leonardo.WinUI.Motion`)

1. Easing and duration factories for both Composition (`CubicBezierEasingFunction`) and Storyboard (`KeySpline`), fed only from tokens.
2. `MotionSettings`: wraps `UISettings.AnimationsEnabled`, raises a change event and offers an in-app override for testing. When animations are off, every helper falls back to a crossfade with `motion.duration.fade`.
3. `DiveIn`: the chosen element flies into the target page and becomes its `PlaceHeader`; the rest of the page staggers in; back reverses the motion. Use `ConnectedAnimationService` or `ContinuumNavigationTransitionInfo`, whichever matches the design language better in testing, and state the reason in the pull request.
4. `Stagger`: up to `motion.stagger.maxGroups` groups, offset `motion.stagger.step`, distance between `motion.distance.enterMin` and `enterMax`, enter easing, opacity with `motion.duration.fade`.
5. `Reflow`: animated repositioning in item panels with the move easing. Compare implicit Composition offset animations with `RepositionThemeTransition` and choose the one closer to the tokens.
6. `Arrive`: a short accent marker on new items that fades away. The hold time is not defined yet; propose a value in the pull request.
7. `Leave`: exit easing, `motion.duration.short`, always combined with a fade.
8. `Transform`: a connected animation between a source element and the panel it becomes.
9. `Respond`: no custom implementation. Document that the platform's pressed states are used.

**Gallery tasks**

1. **Motion** page: every motion can be triggered; a slider slows animations down to one tenth for inspection; the easing curves are drawn; a switch simulates turned-off animations.
2. Use the motions in the scenarios: Files (dive into a folder), Approvals (approve button transforms), Customers (reflow after sorting), Activity (new events arrive).

**Acceptance criteria**

- Every animation can be interrupted, and clicking on quickly jumps to the end state.
- With animations turned off in Windows, every motion becomes a crossfade.
- No linear movement; exits are shorter than entrances.
- All values come from tokens.

## Stage 4 – Leonardo controls

**Goal:** The three controls Leonardo adds to WinUI, used in the scenarios.

1. **`PlaceHeader`:** properties for title and a meta line above it, plus a content slot for a `SummaryLine`. Shrinks to a compact line when its associated `ScrollViewer` scrolls, with `motion.parallax.placeNameFactor` before shrinking. With animations off: no parallax, the shrink happens without animation. Exposed to assistive technology as a level 1 heading.
2. **`SummaryLine`:** a list of items, each with count, label and kind (new, checked out, conflict, custom), rendered as one sentence, for example "Since your last visit: 2 new · 1 checked out · 1 conflict". Each phrase is a toggle filter with a command and an active state. The control hides itself when all counts are zero. Keyboard accessible; screen readers read the full sentence.
3. **`StatusDot`:** kinds new (filled dot in the accent color), checked out (ring in the system caution color) and conflict (filled circle with exclamation mark in the system critical color). Automation name and tooltip text are required.
4. Gallery: one page per control showing all states, and the controls in use in the Files, Approvals and Activity scenarios.
5. Unit tests for logic such as the sentence composition and the visibility rule of `SummaryLine`.

**Acceptance criteria**

- All controls work in Light, Dark and high contrast, by keyboard, with Narrator, with animations off and at the largest Windows text size.

## Stage 5 – WPF resources

**Goal:** WPF apps get Leonardo's values on top of the WPF Fluent theme. No custom controls.

1. `UpInBlue.Leonardo.Wpf`: the generated token dictionaries for Light and Dark, text styles for the type roles, and the accent override for the Fluent theme. Research how the WPF Fluent theme exposes its accent colors and document the approach in the pull request.
2. Motion values as resources (`KeySpline`, `Duration`) and a small helper that respects the system animation setting. Research the best way to read it in WPF and document it.
3. `samples/UpInBlue.Leonardo.Gallery.Wpf`: one window with colors, typography, a list with density switch and a staggered entrance.

**Acceptance criteria**

- In Light and Dark, the WPF sample uses the same values as the WinUI gallery.

## Stage 6 – Apple and web samples

**Goal:** Show that Leonardo works as a dialect on iOS, macOS and the web, and give the skill real examples to point to.

Design with the skill in build mode. Read the Human Interface Guidelines pages "Designing for iOS" and "Designing for macOS" and the pages for every pattern used, and list them in the pull request.

**Apple sample** (`samples/apple/`, runs on a Mac with the current stable Xcode)

1. One SwiftUI multiplatform app with two scenarios: Files and Customers, with invented content.
2. On iOS: navigation stack with large titles, a tab bar for the two scenarios, sheets for editing, swipe actions and context menus, Dynamic Type.
3. On macOS: `NavigationSplitView` with sidebar, the window title as place name, a complete menu bar with shortcuts via `Commands`, a Settings window opened with Command-comma, toolbar, context menus, multiple selection, keyboard navigation, undo and redo.
4. Leonardo values only from `generated/apple`: asset catalog and `LeonardoTokens.swift`. Motion as springs without bounce; Reduce Motion respected.

**Web sample** (`samples/web/`)

1. One standalone page with the Files scenario: plain HTML and CSS using `generated/web/leonardo.css`, Inter self-hosted.
2. Semantic HTML, keyboard support, visible focus, its own URL per view (hash routing is enough), light and dark mode, reduced motion and forced colors.

**Acceptance criteria**

- The Apple sample builds and runs on iOS (simulator) and macOS; the Mac version uses the menu bar and Settings window, the iOS version does not imitate Mac patterns and vice versa.
- The web sample passes a keyboard-only walkthrough and works with reduced motion and forced colors.
- No literal design values in either sample.

## Stage 7 – Claude Code plugin and skill

**Goal:** Other repositories of up in blue get the skill `leonardo` as a plugin, so Claude Code designs, revises and reviews UI platform-correctly.

The skill already exists as a complete draft in `claude/skills/leonardo`. This stage turns it into a plugin and completes it with what the library now offers.

1. Check the current official Claude Code documentation on plugins, skills and hooks before you start; do not rely on memory. Turn `claude/` into a plugin named `leonardo` accordingly.
2. Complete `references/platforms/windows.md` with the actual resource keys, controls and motion helpers of `UpInBlue.Leonardo.WinUI` and `UpInBlue.Leonardo.Wpf`, with correct and incorrect XAML examples taken from the gallery.
3. Complete `ios.md`, `macos.md` and `web.md` with short examples from the stage 6 samples.
4. Check that every URL in `references/sources.md` still resolves; replace moved pages.
5. Review the skill's `description` so that it triggers for UI design, UI changes and usability reviews, and not for unrelated coding tasks.
6. Document installation in the README: as a plugin for the team, plus `claude/settings-snippet.json` for the web access permissions.
7. Test the skill in a separate scratch repository in all three modes: build a small WinUI page, revise a deliberately poor SwiftUI view, and review a web page. Attach the results to the pull request.

**Acceptance criteria**

- In the scratch repository, the skill is used for the three tasks, reads official sources before designing, and names them.
- For the SwiftUI view, the skill applies Mac conventions on macOS and iOS conventions on iOS.
- The review result follows the report format in `references/modes/review.md`.

## Stage 8 – Check tool and hook

**Goal:** Literal design values and common accessibility mistakes are caught automatically while Claude Code edits UI code.

1. A check tool written in C# that scans files outside generated folders:
   - `.xaml`, `.cs`: literal colors, font sizes, corner radii, durations, key times and key splines; spacing values that are not tokens; custom backdrops or brushes that imitate glass; removed or restyled focus visuals.
   - `.swift`: literal colors (`Color(red:…)`, hex helpers), fixed font sizes instead of text styles, literal animation durations, springs with bounce.
   - `.css`, `.scss`, `.html`, `.tsx`: literal colors and font sizes instead of `--leonardo-*` properties, `outline: none` without replacement, transitions without a `prefers-reduced-motion` rule, clickable `div` elements.
   - Output: file, line, rule and suggestion.
2. A hook that runs the check tool after Claude Code edits files of these types and reports violations. Check the current hook documentation first.
3. Ship the check tool and hook with the plugin from stage 7.

**Acceptance criteria**

- Adding a literal color to a gallery page, a SwiftUI view and the web sample produces a reported violation each.
